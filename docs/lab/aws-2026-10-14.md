## Findings and corrections

The initial scoped policy allowed `ec2:AllocateAddress` but omitted the dependent `ec2:AllocateIpamPoolCidr` permission. A real allocation was denied even though simulation of AllocateAddress alone passed. The runbook now includes the dependent action and the regionless IPAM pool ARN format.

AWS returned `InvalidIPAddress.InUse` when ReleaseAddress immediately followed successful disassociation. KubeIP previously exited with the allocation and intent retained. Commit `e31b24b` retries that specific error at one-second intervals, at most ten retries, respecting cancellation. Other release errors still retain intent and return an error.

EKS attached multiple interfaces to each node. After EIP disassociation, the test node had no ephemeral public address. The same commit allows IPAM assignment to its primary interface without requiring a preexisting public address. The legacy preallocated-address mode retains its existing requirement. Regression tests reproduced both problems before the fixes and passed afterward.

This topology needs API connectivity independent of the managed EIP. The lab added private EC2 and EKS Auth endpoints, with private DNS and HTTPS ingress restricted to the lab VPC, and used the private EKS API endpoint. The candidate image was cached before switching its lab pull policy to `IfNotPresent`. Production deployments need an appropriate image and credential retrieval path too. Endpoint connectivity and IAM updates were eventually consistent during the test; the agent retained state through those delays. Reachability Analyzer confirmed the EKS Auth network path, and its temporary analysis and path were removed.

## Limits

This was one region, one public IPv4 pool, two disposable nodes, and an AMD64 candidate image. Allocation rejection was tested through IAM denial; full pool exhaustion was not tested. The lost response and delayed discovery were injected around successful real API calls. Default Node-status waiting, multi-region IPAM, BYOIP, IPv6, large-scale concurrency and abrupt node deletion were not part of this AWS run. Retained allocations after abrupt node loss still require explicit ownership-aware cleanup.
