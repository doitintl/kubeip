## Observed results

- Assignment and legacy label: reserved `35.192.229.43`, published `kubip_assigned=35-192-229-43`, removed readiness taint, preserved unrelated template label and annotation. Restart reused the persisted reservation.
- Node-status readiness: cloud attachment can precede Node status by tens of seconds or minutes. The default wait retained the label/readiness gate during that interval. Remaining lifecycle tests used the documented `WAIT_FOR_NODE_ADDRESS=false` option after independently verifying the cloud attachment.
- Metrics: healthy process returned 200 while assignment readiness returned 503 during startup/failure, then 200 after success. Assignment errors and repair errors were counted. Inventory retained previous values and timestamp while reporting `inventory_up=0` after a connection reset, then recovered to one assigned reservation and zero available. Metrics were accessed only through local port forwarding.
- Drift: after the filter fix, restored the saved reservation from a missing access config, including restart recovery. Refused to take the reservation while attached to the disposable holder VM, preserving the managed node's temporary IP. Once freed, restored the saved reservation from the ephemeral replacement. A subsequent periodic missing-access-config test also restored it.
- Completion uncertainty: initial transport failures left pending intent and both taints intact across container restarts. Recovery stopped the agents, drained the lab nodes, inspected attachments and completed cloud operations, then cleared only their pending assignment state.
- Completion success and exhaustion: with operation-read recovery, two nodes competed for one reservation. One persisted success; the other persisted exhaustion. After configured readiness checks, successful nodes removed both KubeIP taints. Exhausted nodes removed only completion. Restarts preserved both terminal outcomes, and an additional free reservation remained unused by the exhausted node.
- Scheduling: on the exhausted node, an ordinary pod tolerating the readiness taint ran. A pod requiring a reserved IP remained pending.
- Completion tamper: externally changed the completed node's IP while drained. Restart reported that the completed address changed and did not alter the new attachment.
- Denied label cleanup: removed Node patch permission, then stopped the release-enabled agent. It reported the denied label cleanup and retained both the cloud reservation and marker. Restored permission afterward.

- Replacement node: resized the managed pool to zero and back to one. The new Node UID differed, template selector labels survived, and it successfully acquired the reservation and published the assignment label.
- Denied intent persistence: on the fresh replacement node, disabled label publication and denied Node patch permission. Completion-mode intent persistence failed before cloud mutation; the existing ephemeral attachment and both taints remained unchanged.
- Normal release: with a 330-second grace period, shutdown completed in 37 seconds. The assignment label was removed, the reservation returned to RESERVED, and an ephemeral IP was restored. Unrelated template labels remained. The original 30-second shutdown did not finish ephemeral restoration before node replacement.
